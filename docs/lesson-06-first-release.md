## 2. 为什么日历不再存一份任务

`TaskStore` 是数据入口，`TaskController` 是任务操作入口。`CalendarController` 只把这些任务按日期分组，生成六周共 42 个格子，以及选中当天的列表。

例如在日历中修改“提交方案”，调用的仍是原先清单里的 `editTask` 和 `saveDraft`。保存成功后发出 `stateChanged`，清单和日历分别更新自己的展示。这样避免“两份数据忘记同步”。没有日期的任务不进入日历。

日历窗口按需创建，关闭后释放。动态创建的 QML 组件必须与窗口同寿命：它持有界面用到的 QML 上下文。界面联测找到了过早销毁组件的问题，因此在 `AppController._create_window` 中明确设置了对象所有权与父子关系。

## 3. 提醒由调度与发送两部分组成

`reminders.py` 负责决定何时该提醒，`app.py` 中的通知函数负责调用系统托盘通知。

1. 读取未完成且有日期、时刻的任务。
2. 用“任务时间 − 提前分钟数”得到提醒时间。
3. 查询持久化发送记录，跳过相同任务、相同日期时刻和提前量已处理的提醒。
4. 到期的多条任务合并成一次通知；未来任务用单次计时器等待，最长每分钟兜底检查。
5. 任务变更、Windows 时间变化或恢复事件触发重新检查。

删除、完成、取消时刻后，下一次检查读到的就是最新状态，因此不会沿用旧计划。调度测试可注入一个可控的 `now()`，直接模拟“睡眠几小时后恢复”，不必让电脑真的睡几小时。

数据库 v3 新增 `reminder_minutes` 和 `reminder_log`。升级前用 SQLite backup 保留旧库，迁移使用事务。旧任务默认关闭提醒，避免升级后突然补发全部历史待办；新任务默认提前 10 分钟。

发送记录表示向系统请求过通知，不表示用户读过。完全退出／关机时不发送，下次启动补发遗漏；勿扰模式由 Windows 控制。发送前记录用于优先避免崩溃重启后重复弹窗，发送适配器明确失败时会撤回记录；进程恰好在记录与系统调用之间崩溃，仍存在极短的遗漏窗口。

## 4. 全局快捷键与普通快捷键不同

QML 的 Ctrl + Enter 只服务应用内编辑；Windows `RegisterHotKey` 则允许其他应用在前台时也收到操作。`NativeEvents` 接收 `WM_HOTKEY`，转成 Python 方法调用。

剪贴板仅在用户触发录入时读取，不常驻轮询。设置新快捷键时先申请新组合，全部成功后再释放旧组合；失败撤回新增注册，保留旧配置。程序退出主动注销。

显示器位置与快捷键存在同目录 `settings.ini`，不用写入任务表。位置保存为相对工作区比例，适应工作区尺寸变化；找不到原显示器时回到主屏并做边界修正。

## 5. 备份恢复怎样避免破坏当前数据

导出通过 SQLite 自身的 backup 接口产生一致快照，再将临时文件替换成用户选定文件。恢复按顺序执行：

> 只读校验备份 → 展示任务数量 → 用户确认 → 导出当前数据安全副本 → 在一个事务中替换任务和发送记录 → 刷新视图。

格式错误、版本不支持、日期无效或写入失败都不会先清空当前数据。导入时只读取已知字段、用自己的参数化 SQL 写入，不执行备份内的 SQL 定义。备份保存提醒处理记录，避免恢复后反复补发同一计划。

## 7. 建议从这里读代码

先看 `reminder_schedule()`：这是“输入一条任务、输出时间与去重键”的普通 Python 函数。再看 `ReminderService.check()` 如何把它连到数据库与 Qt 定时器，最后看 `ReminderButton.qml` 如何调用 Python 修改提醒。

下一条学习线是 `CalendarController.days` → `CalendarWindow.qml` 的 `Repeater`：Python 提供一个列表，QML 为每个元素生成日期格子。可以先尝试修改格子间距，再观察它如何影响布局。
